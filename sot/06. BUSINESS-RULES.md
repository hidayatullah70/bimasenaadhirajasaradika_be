# SOT — BUSINESS RULES

## PT. Bhimasena Adhirajasa Radhika

> **Status:** Initial Version
> **Purpose:** Menjadi sumber aturan bisnis untuk frontend, API, database, dan implementasi backend.
> **Scope:** Hanya mencakup kebutuhan yang telah ditetapkan dalam PRD.

---

# 1. BUSINESS CONTEXT

PT. Bhimasena Adhirajasa Radhika merupakan perusahaan outsourcing dengan core business:

> **Penyediaan dan pengelolaan manpower outsourcing yang ditempatkan pada lokasi client.**

Layanan utama:

1. Pengamanan / Security
2. Ekspedisi Kurir
3. Man Power
4. Cleaning Service
5. Parkir
6. Loss Prevention

Sistem digunakan oleh:

* Direktur
* HRD
* Finance
* Marketing
* Operasional

---

# 2. ROLE DEFINITIONS

## 2.1 Direktur

Direktur memiliki akses pengawasan dan pengelolaan tertinggi terhadap sistem.

Responsibilities:

* Melihat executive dashboard
* Mengelola user
* Mengelola role
* Melihat data seluruh departemen
* Melihat laporan
* Melihat activity/audit
* Mengawasi client, manpower, placement dan layanan

Direktur tidak boleh mengubah data historis secara sembarangan tanpa audit trail.

---

## 2.2 HRD

Responsibilities:

* Mengelola data employee/manpower
* Mengelola status employment
* Mengelola placement
* Melihat dan mengelola attendance
* Melihat data client/site yang diperlukan untuk penempatan
* Membuat laporan HR

---

## 2.3 Finance

Responsibilities:

* Melihat data client
* Mengelola invoice
* Monitoring status invoice
* Melihat informasi operasional yang diperlukan untuk proses finance
* Membuat laporan finance

Finance tidak memiliki akses untuk mengubah data employee/placement kecuali akses read-only yang diperlukan.

---

## 2.4 Marketing

Responsibilities:

* Mengelola leads
* Mengelola pipeline prospect
* Mengelola informasi client/prospect
* Mengelola aktivitas marketing
* Mengelola proposal tracking
* Membuat laporan marketing

---

## 2.5 Operasional

Responsibilities:

* Mengelola client/site operasional
* Mengelola placement
* Monitoring manpower
* Monitoring attendance
* Monitoring operational issue
* Membuat laporan operasional

---

# 4. USER RULES

## BR-USER-001 — Unique User

Setiap user harus memiliki identifier login yang unik.

Minimum:

* email unique

---

## BR-USER-002 — Active User

Hanya user dengan:

```text
is_active = true
```

yang dapat melakukan login.

---

## BR-USER-003 — Role

Setiap user pada initial version memiliki satu primary role:

```text
direktur
hrd
finance
marketing
operasional
```

---

## BR-USER-004 — Deactivation

User yang tidak lagi memiliki akses sebaiknya:

```text
is_active = false
```

dan bukan langsung dihapus.

Tujuannya menjaga histori aktivitas.

---

## BR-USER-005 — Audit

Perubahan berikut wajib tercatat:

* perubahan role
* aktivasi user
* deaktivasi user
* perubahan permission yang relevan

---

# 5. EMPLOYEE RULES

## BR-EMP-001 — Employee Number

Setiap employee wajib memiliki:

```text
employee_no
```

yang unique.

---

## BR-EMP-002 — Employment Type

Initial employment type:

```text
tetap
kontrak
harian_lepas
```

---

## BR-EMP-003 — Employee Status

Initial status:

```text
active
inactive
terminated
```

---

## BR-EMP-004 — Active Employee

Employee hanya dapat menerima active placement apabila:

```text
employee.status = active
```

---

## BR-EMP-005 — Historical Employee

Employee yang sudah tidak aktif tidak boleh dihapus apabila masih memiliki:

* attendance
* placement
* histori operasional

Data tetap dipertahankan untuk histori.

---

# 6. CLIENT RULES

## BR-CLIENT-001 — Client Identity

Client memiliki:

```text
client_code
name
```

Client code harus unique.

---

## BR-CLIENT-002 — Client Status

Status client:

```text
active
inactive
```

---

## BR-CLIENT-003 — Active Client

Client yang inactive tidak boleh menerima placement baru.

---

# 7. SITE RULES

## BR-SITE-001 — Site Ownership

Setiap site harus dimiliki oleh satu client.

Relationship:

```text
client 1 → many sites
```

---

## BR-SITE-002 — Site Status

Status:

```text
active
inactive
```

---

## BR-SITE-003 — Active Site

Site hanya dapat digunakan untuk placement apabila:

```text
site.status = active
client.status = active
```

---

# 8. SERVICE RULES

## BR-SERVICE-001 — Initial Services

Sistem initial hanya memiliki enam service:

| Code            | Service               |
| --------------- | --------------------- |
| security        | Pengamanan / Security |
| courier         | Ekspedisi Kurir       |
| manpower        | Man Power             |
| cleaning        | Cleaning Service      |
| parking         | Parkir                |
| loss_prevention | Loss Prevention       |

---

## BR-SERVICE-002 — Stable Code

Service code bersifat stable.

Contoh:

```text
security
```

Nama display dapat berubah tanpa mengubah service code.

---

## BR-SERVICE-003 — Active Service

Service hanya dapat digunakan pada placement apabila:

```text
is_active = true
```

---

# 9. PLACEMENT RULES

Placement merupakan hubungan antara:

```text
Employee
    ↓
Client
    ↓
Site
    ↓
Service
```

---

## BR-PLACE-001 — Required Relationship

Placement wajib memiliki:

* employee
* client
* site
* service
* start_date
* status

---

## BR-PLACE-002 — Placement Status

Initial status:

```text
planned
active
ended
cancelled
```

---

## BR-PLACE-003 — Active Placement

Placement dapat berstatus active hanya jika:

```text
employee = active
client = active
site = active
service = active
```

---

## BR-PLACE-004 — End Date

`end_date` wajib diisi apabila:

```text
status = ended
```

atau:

```text
status = cancelled
```

---

## BR-PLACE-005 — Placement Overlap

Sistem initial tidak mengizinkan employee memiliki dua active placement yang overlap pada periode yang sama.

Jika kebutuhan tersebut muncul di masa depan, business rule harus diperbarui terlebih dahulu.

---

# 10. ATTENDANCE RULES

## BR-ATT-001 — Attendance Context

Attendance harus memiliki konteks:

```text
employee
placement
attendance_date
```

---

## BR-ATT-002 — Attendance Status

Initial status:

```text
present
absent
late
leave
sick
off
```

---

## BR-ATT-003 — Unique Attendance

Employee hanya boleh memiliki satu attendance record untuk kombinasi:

```text
employee_id
placement_id
attendance_date
```

---

## BR-ATT-004 — Valid Placement

Attendance tidak boleh dibuat apabila employee tidak memiliki placement yang valid pada tanggal tersebut.

---

## BR-ATT-005 — Attendance Correction

Perubahan attendance setelah tersimpan harus mencatat:

```text
updated_by
updated_at
```

dan perubahan penting dicatat pada activity/audit.

---

# 11. INVOICE RULES

## BR-INV-001 — Invoice Ownership

Invoice selalu terkait dengan satu client.

---

## BR-INV-002 — Invoice Number

Invoice number wajib unique.

---

## BR-INV-003 — Invoice Status

Initial status:

```text
draft
issued
partially_paid
paid
overdue
cancelled
```

---

## BR-INV-004 — Cancelled Invoice

Invoice cancelled tidak dihapus secara fisik.

Tujuannya menjaga histori dan audit.

---

## BR-INV-005 — Financial Authority

Status financial yang bersifat authoritative harus berasal dari backend/database.

Frontend tidak boleh menganggap label UI sebagai sumber kebenaran.

---

# 12. LEAD / MARKETING RULES

## BR-LEAD-001 — Lead Status

Initial pipeline:

```text
new
contacted
qualified
proposal
won
lost
```

---

## BR-LEAD-002 — Required Lead Information

Lead minimal memiliki:

* company name
* contact name
* source

Contact phone/email digunakan apabila tersedia.

---

## BR-LEAD-003 — Pipeline

Perubahan status lead harus dapat ditelusuri.

Contoh:

```text
new
 ↓
contacted
 ↓
qualified
 ↓
proposal
 ↓
won
```

atau:

```text
qualified
 ↓
lost
```

---

# 13. PUBLIC CONTACT RULES

Landing page dapat menerima inquiry dari public.

Required:

```text
name
contact
message
```

---

## BR-CONTACT-001

Semua public input dianggap untrusted.

---

## BR-CONTACT-002

Frontend melakukan validation untuk UX.

Backend wajib melakukan validation untuk security dan data integrity.

---

## BR-CONTACT-003

Public user tidak boleh melihat:

* employee data
* client data
* invoice
* placement
* attendance
* internal activity

---

# 14. AUDIT RULES

Aktivitas berikut wajib dapat diaudit:

* user creation/update
* role change
* employee update
* placement create/update
* attendance correction
* invoice status change
* lead pipeline change

Minimum audit information:

```text
actor
action
resource
resource_id
timestamp
before
after
```

---

# 15. SOFT DELETE RULE

Data berikut sebaiknya tidak hard-delete apabila sudah memiliki histori:

* employee
* client
* site
* placement
* invoice
* attendance
* activity

Gunakan:

```text
status
```

atau:

```text
is_active
```

sesuai kebutuhan entity.

---

# 16. DATE & TIME RULE

API date:

```text
YYYY-MM-DD
```

Contoh:

```text
2026-09-17
```

Timestamp:

```text
ISO 8601
```

Backend menjadi sumber waktu authoritative.

---

# 17. DATA INTEGRITY

Database/backend harus memastikan:

* foreign key valid
* unique identifier
* valid status
* valid relationship
* valid date range
* authorization
* audit trail

Frontend tidak boleh menjadi satu-satunya tempat enforcement business rule.

---

# 18. SCOPE CONTROL

Business rule tidak boleh digunakan untuk menciptakan fitur baru secara diam-diam.

Apabila terdapat kebutuhan seperti:

* payroll
* accounting
* biometric attendance
* mobile application
* advanced BI
* WhatsApp automation backend

maka harus melalui perubahan SOT terlebih dahulu.

Flow:

```text
Requirement baru
      ↓
Cek SOT
      ↓
Di luar scope?
      ↓
Update SOT
      ↓
Approval
      ↓
Implementation
```

---

# 19. BUSINESS RULE PRINCIPLE

> **SOT First. Business Rule Second. Implementation Third.**

Tidak boleh melakukan implementasi yang bertentangan dengan Business Rules tanpa perubahan dokumen SOT terlebih dahulu.
